### 1. Which format was smallest, and why?

Parquet, at 5.6 MB, versus 14.8 MB (PostgreSQL table+index size), 17.5 MB (CSV), and 38.4 MB (JSONL). 
Parquet is columnar and applies compression (snappy, in your case) per column, which works especially well on repeated/low-cardinality values like status, category_name, and city. 
JSONL is largest because it repeats every field name as a string on every single row, pure text redundancy that CSV and Parquet both avoid.

### 2. Fastest full read? Does that mean it's best for everything?
Parquet: 0.017s median, over 25x faster than PostgreSQL's 0.457s and roughly 27x faster than CSV. 
But full-table dumps aren't a typical analytics workload. 
PostgreSQL is a live, concurrent, transactional system; it supports indexes, joins, partial updates, and many simultaneous readers/writers, none of which a static Parquet file offers. 
So "fastest for a full read of a static snapshot" isn't the same claim as "best storage choice."

### 3. How did filtered retrieval differ between Parquet and PostgreSQL?
Parquet's filtered read is 0.023s, PostgreSQL's is 0.063s. Parquet was faster on the filtered query too, in this run. 
The current query does SELECT * with no index on status, so Postgres is doing a full sequential scan. 
An index on status (CREATE INDEX ON curated.sales_order_lines(status)) would let PostgreSQL use an index scan instead, likely closing or reversing that gap.

### 4. Why is JSON Lines more pipeline-friendly than one JSON array for streaming/append workloads?
A single JSON array requires the entire structure to be valid before any of it can be parsed, you can't append a record without rewriting the closing bracket, and a consumer can't start processing until the whole file is read. 
JSON Lines is one independent JSON object per line, so records can be appended, streamed, and processed one at a time without touching the rest of the file.

### 5. What happens if a partition key has very high cardinality or poor locality?
High cardinality means far too many tiny partitions, each with minimal data but its own directory/file overhead, 
which increases metadata and I/O for negligible per-partition savings. 
Poor locality means queries commonly need many partitions per query, so the partition pruning gains are lost. 
Your own dataset generates 21 month-partitions from a year, month pair, a healthy cardinality; 
if you partitioned by order_id instead, you'd get 50,000 nearly-empty partitions.
