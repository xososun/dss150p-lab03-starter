### How backfilling a historical month would work for this DAG
Airflow ties each DAG run to a data interval using a,
[start, end) window, rather than to a wall-clock trigger time.

With schedule='0 2 * * *' and catchup=True, airflow dags backfill -s 2026-06-01 -e 2026-07-01 would create one DAG run 
per day in June, each with its own data interval and its own run_id, and each would independently 
execute extract, transform, load, then validate.

The idempotency guarantees that make this safe, in principle:

extract re-copies the same three source files and hash-verifies the copy, so re-extracting for any historical run 
produces byte-identical output.

transform is a pure function of the raw snapshot plus run_id, same input, same run_id, same staging/curated output.

load's record_hash-gated UPSERT ... WHERE record_hash <> EXCLUDED.record_hash means resubmitting identical rows writes 
nothing, so a backfilled run can never create duplicate order_id rows in curated.sales_order_lines. 
This is exactly what was proved in the airflow DAG run recovery: the same run resubmitted 49,897 rows and wrote none.

Where this breaks down for this specific pipeline, and why that matters:
data/source/ is a single current snapshot, not a date-partitioned history — there's no orders_2026-06.csv alongside 
orders_2026-07.csv. Every backfilled day, from any historical date, would extract the exact same current files and 
produce the exact same curated rows, just tagged with a different (and historically meaningless) run_id. So while the 
mechanics are idempotent and safe, backfilling here wouldn't actually reconstruct what June looked like — it would just 
needlessly re-run the pipeline 30 times against September's data, wasting compute without producing anything new. 
This is the same reasoning behind our catchup=False decision: there's no time-varying source to catch up on.

Avoiding double loads if the source ever became genuinely time-partitioned (e.g. a daily export file per date, 
or an API queried with a date range): each day's extract would need to pull only that day's slice, keyed by the DAG's 
{{ ds }} (the data interval's start date) rather than always reading the same static files. As long as load's conflict 
target stays order_id and record_hash continues to exclude volatile audit columns, the same UPSERT logic would prevent 
double-counting even across a real backfill — the idempotency mechanism doesn't need to change, only how extract 
selects its input.
